● Now I'll walk through the theory and each piece of code in plain terms.

  The theory: fixed-window rate limiting

  Think of it like a bouncer with a stopwatch and a clicker counter, one per
  visitor (IP address):

  1. When a request arrives from IP 1.2.3.4, check: has 60 seconds passed since
  I last reset this IP's counter?
  2. If yes (or it's a brand-new IP) → reset counter to 1, start the clock now.
  3. If no → bump the counter by 1.
  4. If the counter is now over the allowed max (5) → reject with 429 Too Many 
  Requests. Otherwise let the request through.

  This is called fixed-window because the 60-second window is a fixed clock slot
  (e.g. 00:00–01:00, 01:00–02:00), not a rolling window that follows each
  individual request. The one quirk: right at the boundary between two windows,
  a client could squeeze in 5 requests just before the window flips and another
  5 right after — briefly 10 in ~1 second instead of 5 in 60. That's a known,
  accepted trade-off for how simple it is to build and reason about — good
  enough for stopping brute-force login attempts, not meant to be perfectly
  precise.

  Everything else in the design serves that one idea: where to intercept the
  request, how to store counters safely when multiple requests arrive at once,
  how to identify "who" is calling, and how to clean up so memory doesn't grow
  forever.

  File by file

  RateLimitingFilter.java — the bouncer itself

  This is a servlet filter — code that runs on every incoming HTTP request
  before it reaches your controller, similar to airport security before you
  reach the gate.

  public class RateLimitingFilter extends OncePerRequestFilter {
  OncePerRequestFilter is a Spring helper base class guaranteeing your filter
  logic runs exactly once per request (some server setups can otherwise
  re-dispatch a request internally and run filters twice).

  private final ConcurrentHashMap<String, RequestCounter> countersByIp = new
  ConcurrentHashMap<>();
  This is the "clicker per visitor" — a map from IP address string → their
  current counter. ConcurrentHashMap specifically because multiple requests can
  hit the server at the same instant from different threads; a plain HashMap
  isn't safe under concurrent access and could corrupt itself or lose updates.

  public RateLimitingFilter(
          @Value("${rate-limit.auth.max-requests}") int maxRequests,
          @Value("${rate-limit.auth.window-ms}") long windowMs,
          @Value("${rate-limit.trust-forwarded-header:false}") boolean
  trustForwardedHeader,
          ObjectMapper objectMapper,
          Clock clock) {
  @Value("${...}") pulls a number straight out of application.properties (e.g.
  rate-limit.auth.max-requests=5) and hands it to the constructor — so you can
  tune the limit without touching code. ObjectMapper (Jackson's JSON converter)
  and Clock (a wrapper around "what time is it") are injected as normal Spring
  beans, not properties, because they're full objects, not simple values.

  Why inject Clock instead of just calling System.currentTimeMillis() directly?
  So tests can fake time. A real clock ticks in real time — you can't easily
  unit-test "wait 60 seconds" without actually waiting. By depending on an
  abstract Clock, the test swaps in a fake one it can fast-forward instantly.

  protected boolean shouldNotFilter(@NonNull HttpServletRequest request) {
      return !PATH_MATCHER.match(SecurityConfig.AUTH_PATH_PATTERN,
  request.getRequestURI());
  }
  This is the "only check ID at this specific gate" logic. shouldNotFilter is a
  hook OncePerRequestFilter gives you to skip the filter's work entirely for
  requests you don't care about. Here: if the URL isn't /api/auth/..., skip rate
  limiting completely (so browsing /api/users isn't throttled).

  RequestCounter counter = countersByIp.compute(ip, (key, existing) -> {
      if (existing == null || now - existing.windowStart >= windowMs) {
          return new RequestCounter(now, 1);
      }
      existing.count++;
      return existing;
  });
  This is the actual "click the counter" step, and it's the trickiest bit.
  .compute() is an atomic operation — it looks up the key, runs your logic, and
  stores the result, all as one indivisible step, so two simultaneous requests
  from the same IP can't both read "count = 4" and both write back "count = 5"
  (losing one increment). The logic inside says: no counter yet, or the old
  window is stale (more than windowMs has passed) → start fresh at 1. Otherwise
  → same window, add one.

  if (counter.count > maxRequests) {
      long retryAfterSeconds = Math.max(1, (long) Math.ceil((counter.windowStart
  + windowMs - now) / 1000.0));
      writeTooManyRequests(response, retryAfterSeconds);
      return;
  }
  filterChain.doFilter(request, response);
  If over the limit: compute how many seconds remain until the window resets
  (windowStart + windowMs is when the window ends), write the 429 response, and
  return without calling filterChain.doFilter(...) — that's the equivalent of
  the bouncer physically not letting you through the door. If under the limit,
  filterChain.doFilter(...) passes the request along to the next
  filter/controller, business as usual.

  private String resolveClientIp(HttpServletRequest request) {
      if (trustForwardedHeader) {
          String forwardedFor = request.getHeader("X-Forwarded-For");
          if (StringUtils.hasText(forwardedFor)) {
              return forwardedFor.split(",")[0].trim();
          }
      }
      return request.getRemoteAddr();
  }
  "Who is calling?" getRemoteAddr() is the TCP-connection-level IP — always
  trustworthy, but if you put a reverse proxy (nginx, a load balancer) in front
  of your app later, every request will appear to come from the proxy's own IP,
  not the real visitor. Proxies solve this by adding an X-Forwarded-For header
  with the real visitor's IP. But that header is just text anyone can set
  themselves — a client could fake it to dodge the limiter. So it's only honored
  if you explicitly flip rate-limit.trust-forwarded-header=true, which you'd
  only do once you know a trusted proxy is the one actually setting that header.

  private void writeTooManyRequests(HttpServletResponse response, long
  retryAfterSeconds) throws IOException {
      response.setStatus(HttpStatus.TOO_MANY_REQUESTS.value());
      response.setHeader("Retry-After", String.valueOf(retryAfterSeconds));
      response.setContentType(MediaType.APPLICATION_JSON_VALUE);
      ErrorResponse error = new ErrorResponse(429, "Too many requests...",
  LocalDateTime.now(clock));
      objectMapper.writeValue(response.getWriter(), error);
  }
  Manually building the HTTP response. This has to be done by hand (rather than
  just throwing an exception like a controller normally would) because filters
  run outside Spring MVC's normal exception-handling machinery
  (GlobalExceptionHandler never sees anything that happens in a filter).
  Retry-After is a standard HTTP header telling a well-behaved client "don't
  bother retrying for N more seconds." objectMapper.writeValue(...) serializes
  the ErrorResponse record straight to JSON text into the response body, reusing
  the app's existing error shape.

  @Scheduled(fixedRateString = "${rate-limit.cleanup-interval-ms:300000}")
  void purgeExpiredCounters() {
      long now = clock.millis();
      countersByIp.entrySet().removeIf(entry -> now -
  entry.getValue().windowStart > windowMs * 2);
  }
  The garbage collector for old visitors. Without this, every unique IP that
  ever hits /api/auth/** would sit in the map forever, growing unbounded — a
  slow memory leak. @Scheduled tells Spring "run this method automatically every
  N milliseconds" (here every 5 minutes by default). It removes entries whose
  window ended more than twice the window length ago — the 2x buffer is just a
  safety margin so we never accidentally wipe a counter mid-use.

  private static final class RequestCounter {
      private final long windowStart;
      private volatile int count;
  A tiny plain data holder: when this window started, and how many hits so far.
  volatile on count ensures that when one thread increments it, other threads
  immediately see the new value rather than a stale cached copy — necessary
  because compute() synchronizes the map update itself, but reading
  counter.count afterward (in the if (counter.count > maxRequests) check)
  happens outside that lock.

  SecurityConfig.java — plugging the bouncer into the building

  public static final String AUTH_PATH_PATTERN = "/api/auth/**";
  ...
  .requestMatchers(AUTH_PATH_PATTERN).permitAll()
  One constant reused in two places, so the "which URLs are the auth endpoints"
  definition can't drift out of sync between the security rule and the rate
  limiter's own path check.

  .addFilterBefore(jwtAuthenticationFilter,
  UsernamePasswordAuthenticationFilter.class)
  .addFilterBefore(rateLimitingFilter, JwtAuthenticationFilter.class);
  Spring Security's filter chain is an ordered pipeline — addFilterBefore(X, 
  Y.class) says "insert X right before Y." Order here matters twice over:
  1. Logically: rate limiting should happen first, before any JWT
  parsing/validation work, so an attacker gets rejected cheaply and early rather
  than making the server do more work per rejected request.
  2. Mechanically: Spring needs to already know where JwtAuthenticationFilter
  sits before you can say "put something before it" — that's why the two lines
  are in this specific order (register JWT's position first, then anchor the
  rate limiter to it).

  ---
  AppConfig.java — why Clock lives here, not in SecurityConfig

  @Bean
  public Clock clock() {
      return Clock.systemUTC();
  }
  Simple on its own, but the reason it's a separate file is the interesting
  part: SecurityConfig needs RateLimitingFilter (to register it), and
  RateLimitingFilter needs Clock. If Clock had stayed defined inside
  SecurityConfig, you'd get a loop — to build SecurityConfig, first build 
  RateLimitingFilter, which needs Clock, which is a method on SecurityConfig, 
  which isn't built yet — a circular dependency Spring can't resolve. Moving
  Clock to its own independent class breaks that cycle.

  ---
  In one sentence: every request to /api/auth/** first passes through a per-IP
  click-counter; if a given IP clicks past 5 within 60 seconds, it gets turned
  away with a 429 and a "try again in N seconds" header, and stale counters get
  swept away every 5 minutes so the map doesn't grow forever.

     Internationalization (i18n) for error/validation messages

     Context

     The API currently returns every error/validation message as a hardcoded
     English string (in GlobalExceptionHandler, the two resource exceptions, the
     DTO validation annotations, JwtAuthEntryPoint, and RateLimitingFilter).
     There is zero i18n infrastructure today — no messages*.properties, no
     MessageSource/LocaleResolver. We're adding support for serving localized
     messages based on the client's Accept-Language header (confirmed with user
     — standard REST convention, works for a stateless JWT API with no
     server-side session, including pre-login requests). Confirmed scope:
     support English (default/fallback) + Sinhala (si) at launch, and translate
     embedded English nouns too (e.g. "User", "id", "email" inside "User not
     found with id: '5'"), with automatic fallback to the raw English word if a
     translation entry is ever missing.

     Spring Boot autoconfigures both the MessageSource bean (reads
     classpath:messages*.properties) and the MVC LocaleResolver
     (AcceptHeaderLocaleResolver, reads Accept-Language) purely from
     application.properties — no new @Configuration/@Bean class is needed.
     Confirmed @WebMvcTest slices already import MessageSourceAutoConfiguration,
     so existing controller tests keep a working MessageSource with no extra
     test wiring.

     One layering wrinkle: JwtAuthEntryPoint and RateLimitingFilter are plain
     servlet filters that run before DispatcherServlet, so Spring's MVC-resolved
     Locale/LocaleContextHolder isn't populated yet when they execute. Those
     two must resolve locale via HttpServletRequest.getLocale()
     (servlet-container-level Accept-Language parsing) instead.

     Key design points

     - Never throw NoSuchMessageException. Every messageSource.getMessage(...)
     call uses the 4-arg overload getMessage(code, args, defaultMessage, 
     locale), passing today's hardcoded English string as defaultMessage. This
     is what gives the "fallback to raw English noun" behavior, and also
     protects against our own typos/missing keys degrading to English instead of
     a 500.
     - Key naming: validation.* (Bean Validation messages), entity.*/field.*
     (noun lookup table, keyed by rawWord.toLowerCase()), error.* (everything
     else).
     - GlobalExceptionHandler gets a Locale locale parameter added to each
     @ExceptionHandler method (Spring's exception-handling argument resolution
     supports Locale natively, same as regular controller methods) rather than
     reading LocaleContextHolder inside the body — easier to unit-test
     deterministically.
     - ResourceNotFoundException/DuplicateResourceException keep their existing
     super(String.format(...)) call (so .getMessage() stays a stable English
     string for logs) but also expose resourceName/fieldName/fieldValue via
     getters, so the handler can independently build a localized message,
     translating the nouns via entity.*/field.* lookups.
     - handleValidationErrors additionally translates fieldError.getField()
     (e.g. "email") via the same field.* table when building its joined message;
     fieldError.getDefaultMessage() is already localized automatically once DTO
     annotations use {validation.xxx} codes.
     - JwtAuthEntryPoint: drop the raw authException.getMessage() interpolation
     (that string comes from Spring Security internals, always English, and
     concatenating it into an otherwise-localized sentence would look broken and
     leak internal detail). Replace with a flat error.unauthorized key. Also
     fixes a pre-existing wart while we're in there: hand-rolled String.format
     JSON → proper ErrorResponse + injected ObjectMapper (matches how
     RateLimitingFilter already does it) — safer than manual string/JSON
     escaping.
     - MessageFormat quoting gotcha: the resource-not-found/already-exists
     templates use {2} inside literal single quotes for the field value, e.g.
     "{0} not found with {1}: '{2}'". In MessageFormat syntax (which
     getMessage(code, args, ...) uses under the hood), a single quote is an
     escape char — '{2}' would render as literal text {2}, NOT the substituted
     value. Must double the quotes in the property file:
     error.resource.not-found={0} not found with {1}: ''{2}''.
     - Encoding: spring.messages.encoding=UTF-8 (set explicitly even though it's
     already the default) — the real risk is messages_si.properties must be
     saved as UTF-8 on disk, or the Sinhala glyphs get silently mangled.
     - Sinhala strings below are a best-effort translation to unblock
     implementation, not verified by a native speaker — flagged for a
     native-speaker review pass before shipping.

  So "blocking after a certain amount of time" isn't a ban — it's a rolling
  quota: once the 60-second window that started with the first request in the
  burst has fully elapsed, the very next request for that IP starts a brand-new
  window and counting begins from 1 again.

  Memory cleanup (separate from blocking)

  @Scheduled(fixedRateString = "${rate-limit.cleanup-interval-ms:300000}")   // 
  every 5 min by default
  void purgeExpiredCounters() {
      countersByIp.entrySet().removeIf(entry -> now -
  entry.getValue().windowStart > windowMs * 2);
  }
  This just deletes old, unused IP entries from the map every 5 minutes so
  memory doesn't grow forever — it has no effect on whether a request is
  blocked, since a request either finds its window still valid or creates a
  fresh one regardless of whether cleanup has run.
